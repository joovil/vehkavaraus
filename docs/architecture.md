# Architecture

> **Note:** This documentation was generated by Claude Opus 5.5 (Anthropic) based on the project source code.

## Overview

```
Browser
  │
  ├─ Pages / components (src/app, src/components)
  │     ├─ reads:  server components & server actions ─────────────┐
  │     └─ writes: src/lib/services/*Service (fetch wrappers)       │
  │                    │ apiFetch → NEXT_PUBLIC_API_URL/api/...     │
  │                    ▼                                            │
  │            Route handlers (src/app/api)                         │
  │                    │                                            │
  │                    ▼                                            ▼
  │            Repositories (src/database/repositories) ──► Kysely ──► PostgreSQL
  │
  └─ src/middleware.ts (redirects + admin page protection)
```

The layering follows [conventions.md](../conventions.md):

- **Server actions** (suffix `Action`) are for reads where error handling is not needed.
- **API routes** handle create, update and delete. Client code calls them only through wrappers in `src/lib/services/` (suffix `Service`), which use `apiFetch` (`src/lib/utils/apiFetch.ts`).
- **Repositories** in `src/database/repositories/` are the only place that queries the database directly: `userRepository`, `gameRepository`, `borrowRepository`, `verificationRepository` and `adminRepository`.

Types are defined as zod schemas in `src/types/subtypes/`. TypeScript types and the Kysely `Database` interface are inferred from these schemas.

## Database client

`src/database/index.ts` exports a single Kysely instance:

- `NODE_ENV=production`: `NeonDialect`, connecting to `DATABASE_URL`.
- Otherwise: `PostgresDialect` with a `pg` pool, using the `DB_*` variables.

Both use `CamelCasePlugin`. Columns are snake_case in SQL and camelCase in TypeScript.

## Data model

See also [database.plantuml](database.plantuml).

Enums:

- `role`: `unverified` | `user` | `admin`
- `borrow_status`: `free` | `borrowed` | `late`

| Table           | Key columns                                                                                                                                       |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `users`         | `id` uuid PK, `username` unique (longer than 2 chars), `password_hash`, `email`, `apartment`, `role` (default `unverified`)                        |
| `games`         | `id` serial PK, `name` unique, `borrow_status` (default `free`), `available_date`, `image_url`, `current_borrow` → `borrows.id`                    |
| `borrows`       | `id` serial PK, `borrower_id` → `users.id`, `game_id` → `games.id`, `borrow_date` (default today), `due_date` (default today + 1 week), `return_date` |
| `verifications` | `verification_key` uuid PK, `user_id` → `users.id` (cascade delete), `used` boolean                                                                |

### Borrow lifecycle

```
 free ──(POST /api/borrows)──► borrowed ──(daily cron, available_date passed)──► late
  ▲                               │                                               │
  └──────────(POST /api/borrows/return/[id])──────────────────────────────────────┘
```

- **Borrow** (`createBorrow`): runs in a transaction. It checks the game is `free`, inserts a `borrows` row, and sets the game's `borrow_status='borrowed'`, `available_date=due_date` and `current_borrow`.
- **Return** (`completeBorrow`): runs in a transaction. It sets `return_date` on the borrow and resets the game to `free` with `available_date` and `current_borrow` set to null.
- **Late check** (`lateGameCheck`): sets `borrow_status='late'` for every game whose `available_date < NOW()`.

## Authentication & authorization

Config: `src/app/api/auth/[...nextauth]/auth.ts`.

- next-auth **Credentials provider**. Users are looked up by username, and passwords are compared with bcrypt (10 rounds when hashing).
- **JWT sessions**. The user object (`id`, `username`, `email`, `apartment`, `role`) is stored in `token.user` and exposed as `session.user`. Calling `update()` from the client merges new values into the token. This is used after email verification to set the role to `user`.
- `auth()` is a helper around `getServerSession(authOptions)` for server code.
- The custom sign-in page is `/login`.

### Signup & email verification

See [user_creation.plantuml](user_creation.plantuml).

1. `POST /api/signup` validates the input with zod, hashes the password and creates the user with the role `unverified`.
2. `sendVerificationEmail` stores a random UUID in `verifications` and sends an email via Resend from `noreply@vehkavaraus.joovil.dev`. The email links to `NEXT_PUBLIC_API_URL/signup/verification/<key>`.
3. The verification page calls `GET /api/auth/verification/<key>`. This marks the key used and sets the user's role to `user`.
4. Unverified users see a "resend verification" prompt (`src/components/ResendVerification.tsx`), which calls `POST /api/auth/verification`.

### Middleware (`src/middleware.ts`)

| Rule                                                                          | Effect                    |
| ----------------------------------------------------------------------------- | ------------------------- |
| `/`                                                                           | redirect to `/games`      |
| Not logged in and path starts with `/user`                                    | redirect to `/login`      |
| Logged in and on `/signup` or `/login`, except unverified users on a verification page | redirect to `/games`      |
| Logged in and on another user's `/user/...` page                              | redirect to own user page |
| `/admin/*` without the `admin` role, **except in development**               | redirect to `/games`      |

The middleware does not run for any other `/api/*` route. Those routes check the session themselves where needed.

Roles are granted by hand in SQL. There is no UI for it:

```sql
UPDATE users SET role = 'admin' WHERE username = '...';
```

## Pages

| Route                         | Description                                                        |
| ----------------------------- | ------------------------------------------------------------------ |
| `/games`                      | Game grid. Verified users can borrow                               |
| `/login`, `/signup`           | Authentication                                                     |
| `/signup/verification/[id]`   | Email verification landing page                                    |
| `/user/[username]`            | Active borrows (return button) and settings (apartment, password)  |
| `/admin/admin-panel`          | All games with status, borrow history, force return, delete        |
| `/admin/add-game`             | Upload a new game with an image                                    |

## Image storage

- Admins upload images at `/admin/add-game`. The image is compressed in the browser with `compressorjs` (quality 0.5), then sent to `POST /api/admin/games`.
- The API stores it in Vercel Blob at `vehka/games/<name>`, which requires `BLOB_READ_WRITE_TOKEN`.
- `next.config.mjs` allows `next/image` to load from the project's blob host.
- Deleting a game also deletes its blob.

## Scheduled jobs

`vercel.json` defines one cron job:

```json
{ "path": "/api/cron/late-check", "schedule": "0 8 * * *" }
```

Vercel sends `Authorization: Bearer <CRON_SECRET>`. The endpoint rejects any request without it.

## Deployment

- **Hosting:** Vercel (Next.js app and cron).
- **Database:** Neon PostgreSQL. Apply migrations with `pnpm migrate:prod`, with `DATABASE_URL` set.
- **Storage:** Vercel Blob.
- **Email:** Resend. The `vehkavaraus.joovil.dev` domain must be verified in Resend.
- Required production env vars: `DATABASE_URL`, `NEXTAUTH_SECRET`, `NEXTAUTH_URL`, `NEXT_PUBLIC_API_URL`, `RESEND_API_KEY`, `BLOB_READ_WRITE_TOKEN`, `CRON_SECRET`.
