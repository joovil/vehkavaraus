## Environment variables

Next.js loads env files based on `NODE_ENV` (`.env.development` for `pnpm dev`, `.env.test` for Vitest, `.env.production` for builds). `*.local` variants override them.

| File                | Committed | Purpose                                                   |
| ------------------- | --------- | --------------------------------------------------------- |
| `.env.development`  | yes       | Local dev DB (port 5432), auth and URL settings           |
| `.env.test`         | yes       | Test DB (port 5433)                                       |
| `.env.production`   | no        | Production values (gitignored)                            |
| `.env*.local`       | no        | Local secrets/overrides, e.g. `RESEND_API_KEY` (gitignored) |

| Variable                | Required                      | Used in                                                  | Example / dev value          |
| ----------------------- | ----------------------------- | -------------------------------------------------------- | ---------------------------- |
| `DB_NAME`               | dev & test                    | `src/database/index.ts`, migration scripts               | `vehka`                      |
| `DB_HOST`               | dev & test                    | same                                                     | `localhost`                  |
| `DB_USER`               | dev & test                    | same                                                     | `postgres`                   |
| `DB_PASSWORD`           | dev & test                    | same                                                     | `pass`                       |
| `DB_PORT`               | dev & test                    | same                                                     | `5432` (dev), `5433` (test)  |
| `DATABASE_URL`          | production, `migrate:prod*`   | `src/database/index.ts`, `migrateProd.ts`                | Neon connection string       |
| `NEXTAUTH_SECRET`       | yes                           | next-auth (JWT signing)                                  | any random string            |
| `NEXTAUTH_URL`          | yes                           | next-auth                                                | `http://localhost:3000`      |
| `NEXT_PUBLIC_API_URL`   | yes                           | `src/lib/utils/apiFetch.ts`, verification email link     | `http://localhost:3000`      |
| `RESEND_API_KEY`        | yes (placeholder in dev)      | `src/lib/utils/sendVerificationEmail.ts`                 | `re_...`                     |
| `BLOB_READ_WRITE_TOKEN` | for adding/deleting games     | `@vercel/blob` (read implicitly)                         | `vercel_blob_rw_...`         |
| `CRON_SECRET`           | for the cron endpoint         | `src/app/api/cron/late-check/route.ts`                   | any random string            |
| `NODE_ENV`              | set by Next.js / Vitest       | `src/database/index.ts`, `src/middleware.ts`             | `development`                |

Things to be aware of:

- `NODE_ENV=production` switches the database client to Neon (`DATABASE_URL`). Anything else uses the local `DB_*` settings.
- When `NODE_ENV=development`, **admin pages are not access-protected** by the middleware. The `/api/admin/*` handlers require the `admin` role in every environment.
- `.env.development` contains a placeholder `RESEND_API_KEY` (`re_placeholder`). Without it the Resend client throws when `/api/signup` is loaded. With the placeholder signup works but no email is sent. For real emails, put a working key and a verified sender domain in `.env.development.local`. Without a real key, verify a user by hand: open `/signup/verification/<verification_key>` in the browser using the key from the `verifications` table, or set the user's `role` to `user` in SQL.

## Local database

The app's database runs in Docker. The Next.js app itself runs on the host.

| Purpose | Command        | Container           | Port | Compose file       |
| ------- | -------------- | ------------------- | ---- | ------------------ |
| Dev     | `pnpm devdb`   | `vehkavaraus_db`    | 5432 | `compose.dev.yml`  |
| Test    | `pnpm testdb`  | `vehkavaraus_test`  | 5433 | `compose.test.yml` |

- Both containers mount `database/init.sql`, which creates the `vehka` database on first start.
- Dev data is bind-mounted to `database/data/` (gitignored). Test data uses the named volume `db_test_data`.
- Credentials: user `postgres`, password `pass`.
- Open a `psql` shell with `pnpm enterdb` or `pnpm entertestdb`, then connect with `\c vehka`.
- `.vscode/settings.json` contains SQLTools connections for both databases.

### Seeding

`database/add_games.sql` inserts 11 games, with images already hosted on the production blob store:

```bash
docker exec -i vehkavaraus_db psql -U postgres -d vehka < database/add_games.sql
```

### Resetting the dev database

```bash
pnpm resetdb     # stops the container and deletes database/data
pnpm devdb
pnpm migrate:dev
```

## Migrations

Migrations use the Kysely `Migrator` with `FileMigrationProvider`. They live in `src/database/migrations/`, and the runner scripts are in `src/database/migrations/utils/`.

| Command                  | Target                                 |
| ------------------------ | -------------------------------------- |
| `pnpm migrate:dev`       | Local dev DB (`.env.development`)      |
| `pnpm migrate:test`      | Test DB (`.env.test`, port 5433)       |
| `pnpm migrate:dev:down`  | Roll back one migration on the dev DB  |
| `pnpm migrate:prod`      | Neon (`DATABASE_URL`)                  |
| `pnpm migrate:prod:down` | Roll back one migration on Neon        |

`migrate:prod` loads env through `@next/env`, so `DATABASE_URL` can be set in `.env.production`, in `.env.local` or in the shell.

### Adding a migration

1. Create `src/database/migrations/<YYMMDD>_<description>.ts`. Migrations run in alphabetical order, so the date prefix sets the order.
2. Export `up` and `down`:

   ```ts
   import { Database } from "@/types";
   import { Kysely } from "kysely";

   export const up = async (db: Kysely<Database>): Promise<void> => {
     await db.schema.alterTable("games").addColumn("foo", "text").execute();
   };

   export const down = async (db: Kysely<Database>): Promise<void> => {
     await db.schema.alterTable("games").dropColumn("foo").execute();
   };
   ```

3. Update the zod schemas and the Kysely `Database` types in `src/types/`.

The migration Kysely instances use `CamelCasePlugin`, so camelCase identifiers (e.g. `imageUrl`) are converted to snake_case (`image_url`).

## Testing

Tests use Vitest (`vitest.config.mts`). Specs match `src/**/*.spec.ts` and run one file at a time against the **test database**. `src/tests/setup.ts` truncates the `borrows`, `games`, `verifications` and `users` tables before the tests run.

```bash
pnpm testdb          # start test DB on port 5433
pnpm migrate:test    # create the tables in the test DB
pnpm vitest run      # run all tests once
pnpm test            # watch mode
pnpm coverage        # single run with coverage
```

Coverage excludes `src/app` and `src/components`.

## Linting, formatting and type checking

```bash
pnpm lint         # ESLint: next/core-web-vitals + next/typescript
pnpm checkTypes   # tsc --noEmit
npx prettier --write .
```

- Prettier uses `prettier-plugin-tailwindcss` and `singleAttributePerLine` for `.tsx` files.
- ESLint allows unused variables prefixed with `_`.

## Known issues

These were found while writing the documentation and have not been fixed yet:

- **`migrate:dev:down` imports `migrateDev.ts`, which runs `migrateToLatest()` when it is imported.** It may migrate up before it rolls back.
- **`src/lib/services/borrows/getBorrowByGameIdService.ts`** calls `/api/borrows/[id]`, which does not exist.
- **`src/app/api/signup/route.ts`** uses `if ((error.code = "23505"))`, which is an assignment, not a comparison. Every database error other than "username too short" is reported as `409 Username already in use`.
- **`database/test_queries.sql`** refers to old tables (`person`, `game`).
- **The `kysely` script** has no kysely-ctl config file.
- **Debug and stub routes** are still present: `/debug`, `/user`, `/user/newUser`, `/games/[id]` and `/api/test`.
